## Context

`lessons-page`／`commissions-page` 的 design.md 都把垃圾訊息防護列為已知風險、留待之後處理。兩個表單目前結構相似（Client Component + 直接呼叫 Server Action），這裡要在不重新設計整體架構的前提下疊加防護層。

## Goals / Non-Goals

**Goals:**
- 過濾掉大多數自動化垃圾機器人（不需要人工介入、不誤傷真人使用者）
- 不需要新的第三方服務或 API 金鑰

**Non-Goals:**
- 不做到能擋下「真人手動操作的垃圾訊息」——蜜罐/時間戳只防自動化機器人，這是本方案的固有限制
- 不做 IP 層級的速率限制（需要額外的儲存/基礎設施，超出這次範圍）

## Decisions

**1. 用蜜罐欄位＋送出時間戳，不用 reCAPTCHA／Turnstile**
兩個表單各自加一個視覺隱藏（`sr-only`／`position: absolute; left: -9999px`，不是 `display: none`——後者部分機器人會偵測並跳過）的文字欄位（例如命名為 `website`，故意取一個機器人常見的自動填值目標名稱），以及一個表單載入時記錄的 `Date.now()` 隱藏欄位。送出時若蜜罐欄位非空，或送出時間與載入時間差小於 1.5 秒，視為機器人。
理由：這是最低成本、不需要向第三方服務註冊拿金鑰、對真人使用者完全無感（不會看到驗證碼、不會被要求多做任何操作）的防護方式，能擋下絕大多數不具備瀏覽器渲染能力的自動化表單機器人（這類機器人是目前最常見的垃圾訊息來源）。真正客製化針對這個網站寫的機器人可以繞過，但那不是本方案要解決的問題等級。

**2. 偵測到疑似機器人時，回應「看起來成功」但不寫入資料庫**
`validateLessonInquiry`／`validateCommissionInquiry` 新增的機器人檢查獨立於一般欄位驗證：一般驗證失敗會回傳結構化錯誤讓表單顯示；機器人偵測觸發時，Server Action 直接回傳 `{ ok: true }`（如同成功），但跳過 `prisma.commission.create`。
理由：蜜罐機制的核心前提是「不讓對方知道自己被偵測到」——如果機器人收到明確的錯誤訊息，寫機器人的人會很快發現這個欄位是蜜罐並移除自動填值邏輯，防護就失效了。讓它「看起來成功」是這個技巧本身要求的行為，不是要誤導真人使用者（真人不會觸發這個分支）。

**3. 時間戳門檻設為 1.5 秒，不做成可調整的設定**
寫死在驗證函式裡，不透過環境變數或後台設定調整。
理由：這是一個防禦性的技術細節，音樂人不需要、也不應該透過後台介面調整這種東西；1.5 秒對任何需要先看到表單欄位、思考、點擊、輸入至少幾個字元的真人來說都綽綽有餘，同時足以擋下大多數毫秒等級提交的自動化腳本。

## Risks / Trade-offs

- [風險] 瀏覽器自動填表工具（密碼管理器等）理論上可能誤填蜜罐欄位 → 緩解：蜜罐欄位命名與型別（純文字、非 email/password）不太會觸發密碼管理器的自動填值邏輯；且時間戳門檻只有 1.5 秒，即使密碼管理器誤填也不太可能同時觸發「送出時間過短」，除非使用者填完後幾乎立刻送出
- [風險] 進階機器人（真的用無頭瀏覽器渲染頁面、模擬人類延遲）可以繞過這兩層防護 → 緩解：已於 Decision 1 記錄為本方案的固有限制，這類進階機器人成本高、通常不會針對小型個人網站，真的出現時再評估更強的方案
