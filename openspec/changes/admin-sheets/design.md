## Context

`admin-profile` 已建立「Server Component 查詢 + Client Component 表單 + Server Action 存檔 + 前後端共用驗證」的完整後台頁面模式，這裡是第二次套用同一模式，差異在於這是清單式資料（多筆商品，各自獨立新增/編輯/刪除），比 `ProfileConfig` 的單筆設定更接近 `FeaturedVideoManager` 的操作型態。

## Goals / Non-Goals

**Goals:**
- 音樂人能在 `/admin/sheets` 檢視所有樂譜商品（含未上架）及其銷售量
- 能新增、編輯、刪除樂譜商品的基本欄位，並切換上下架
- 表單驗證前後端一致，沿用既有 Server Action 模式

**Non-Goals:**
- 不做檔案上傳（見 proposal.md Impact）
- 不做浮水印圖片生成
- 不做完整營收報表

## Decisions

**1. 檔案相關欄位暫時用純文字輸入框，不假裝有上傳功能**
`pdfFileKey`、`sampleImages`（陣列，用換行分隔的 textarea 輸入多個網址）、`audioSampleUrl` 三個欄位直接對應資料庫欄位的文字輸入，介面上明確標註「暫時：貼上網址」的說明文字。
理由：這是與使用者確認過的階段性做法——R2 憑證還沒準備好，與其擋住整個 A3 等 R2，不如先讓「管理商品基本資訊、上下架」這個對音樂人最常用的操作先能用；等 R2 備妥後，只需要把這三個輸入框換成真正的上傳元件並在成功後把回傳的網址/路徑填入同樣的表單欄位，資料庫 schema 完全不用改，替換成本低。

**2. 銷售量用 `_count` 搭配關聯篩選，只算 `Order.status === SUCCESS` 的 `OrderItem`**
查詢 `SheetMusic` 時帶入 `_count: { select: { orderItems: { where: { order: { status: "SUCCESS" } } } } }`，列表顯示這個數字。
理由：`PENDING`／`FAILED` 的訂單不代表真的賣出，若不篩選會讓銷售量虛高，誤導音樂人對熱門商品的判斷。這與 A5（訂單管理）之後要做的「收入統計」邏輯一致，提前在這裡對齊可以避免兩處各自定義「什麼算作銷售」而互相矛盾。

**3. `difficulty`／`genre` 維持自由文字，不做成固定下拉選單**
沿用 `SheetMusicBrowser.tsx` 現有的模式（前台篩選選項是 `Array.from(new Set(sheets.map(...)))` 動態算出來的，不是寫死的常數清單），後台新增/編輯也用一般文字輸入框，不引入新的固定選項清單。
理由：如果後台改成固定下拉選單，等於是在沒有明確規格要求、且前台早就選擇自由文字模式的情況下，另外引入一份需要同步維護的「合法選項清單」，徒增複雜度；音樂人打字輸入曲風/難易度的操作成本很低，維持自由文字與前台行為一致更簡單。

**4. 已有訂單關聯的樂譜不能刪除，只能下架**
`deleteSheetMusic` 執行前先檢查是否存在關聯的 `OrderItem`；若有，拒絕刪除並提示改用下架。
理由：`OrderItem.sheetMusicId` 是必要的外鍵關聯（`SheetMusic` 沒有設定 `onDelete: Cascade` 或 `SetNull`），直接刪除會讓既有訂單的商品資訊消失或造成資料庫層級的外鍵錯誤；下架（`isPublished: false`）已經足以達到「前台不再顯示、不能再被購買」的效果，且保留了歷史訂單的完整商品資訊，這對 A5 訂單管理頁面之後要顯示「买了什麼」是必要的。

## Risks / Trade-offs

- [風險] 純文字網址欄位讓非工程背景的使用者容易貼錯格式（例如貼到本機路徑而非公開網址）→ 緩解：已在介面上明確標註這是暫時性做法，且這三個欄位在 R2 整合完成前，音樂人本來就需要自己先把檔案上傳到某處取得網址，這件事本身無法避免，本次改動不使其變得更差
- [風險] `sampleImages` 陣列用換行分隔的 textarea 輸入，格式解析可能有邊界情況（空白行、多餘空格）→ 緩解：儲存前逐行 `trim()` 並過濾空字串，這是簡單且可預期的處理方式
