## Context

`Commission` 資料表已經有兩個前台寫入來源在運作（`lessons-page`／`commissions-page`），這裡是第一次讀取／操作這份資料的後台介面。與 `admin-orders` 類似，這是聯繫紀錄而非可自由編輯的商業內容，寫入操作應該被限制。

## Goals / Non-Goals

**Goals:**
- 音樂人能一眼看出哪些詢問還沒處理，優先處理未讀項目
- 標記已處理的操作要即時、不需要整頁重新整理

**Non-Goals:**
- 不做刪除／編輯委託內容的介面（見 proposal.md）
- 不做新委託的即時通知

## Decisions

**1. 排序：未處理優先於已處理，各自區塊內依時間新到舊**
查詢時 `orderBy: [{ isHandled: "asc" }, { createdAt: "desc" }]`（`false` 排在 `true` 前面，因為 boolean 的 `asc` 排序 `false < true`）。
理由：「看板」的核心使用情境是音樂人打開頁面時，第一眼就要看到需要處理的項目，而不是被舊的、已處理的紀錄淹沒；已處理的項目仍保留可見（不隱藏），但排在後面作為歷史紀錄查閱。

**2. 唯一允許的寫入操作是切換 `isHandled`，用單一輕量 Server Action**
`toggleCommissionHandled(id, isHandled)`：不需要額外的欄位驗證（純 boolean 切換），對應的 UI 是每筆紀錄旁的核取方塊，勾選後立即呼叫並樂觀更新畫面。
理由：這是這個頁面唯一需要的寫入行為，沒有必要比照其他管理頁面建立完整的新增/編輯表單基礎架構（`validation/*.ts`、多欄位表單）——`Commission` 的內容本來就是訪客自己填寫送出的，音樂人不該、也不需要修改別人的委託內容。

**3. 三種類型（`LESSON`／`TRANSCRIPTION`／`COLLABORATION`）混合顯示在同一個清單，用標籤區分，不分開三個頁籤**
清單不依類型分頁籤或分區塊，而是每筆紀錄前面加一個類型標籤（教學詢問／採譜委託／合作邀約），全部依 Decision 1 的排序規則混合排列。
理由：這裡的時效性（誰先聯繫、誰還沒處理）比類型分類更重要——`admin-services` 依類型分組是因為那些是要對應到不同前台頁面的獨立商業設定，彼此不需要比較時間先後；但委託/詢問是「有人聯繫我」的通知性質資料，音樂人更需要的是「最近有誰聯繫、還有誰沒處理」的統一時間軸視角，分頁籤反而會讓人漏看其他類型裡更早、更急迫的未處理項目。

## Risks / Trade-offs

- [風險] 沒有刪除功能，垃圾/測試訊息會一直留在清單裡 → 緩解：目前沒有對外公開的垃圾訊息防護（`lessons-page`／`commissions-page` 的 design.md 都已記錄這個已知缺口），這裡選擇不做刪除是保守選項（避免音樂人不小心刪掉真實委託），之後若垃圾訊息成為實際困擾，屆時再評估是否需要刪除或封存功能
